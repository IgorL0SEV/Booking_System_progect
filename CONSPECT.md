## 1. От бизнес-задачи к сущностям

В задании сформулирован кейс, а не схема. Из него выделяются три сущности:

| Сущность | Что описывает | Ключевые атрибуты |
|---|---|---|
| `User` | гость заведения | имя, телефон (уникальный) |
| `Table` | стол в зале | номер, число мест, расположение |
| `Booking` | факт брони | кто, какой стол, начало и конец |

Связи: `Booking` ссылается на `User` и `Table`, то есть это связующая сущность между
гостем и столом. У пользователя может быть много броней, у стола — тоже.

## 2. Схема базы

```sql
CREATE TABLE IF NOT EXISTS users (
    id         SERIAL PRIMARY KEY,
    name       TEXT NOT NULL,
    phone      TEXT NOT NULL UNIQUE,
    created_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE TABLE IF NOT EXISTS tables (
    id       SERIAL PRIMARY KEY,
    number   INT NOT NULL UNIQUE CHECK (number > 0),
    seats    INT NOT NULL CHECK (seats >= 1),
    location TEXT
);

CREATE TABLE IF NOT EXISTS bookings (
    id         SERIAL PRIMARY KEY,
    user_id    INT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    table_id   INT NOT NULL REFERENCES tables(id) ON DELETE CASCADE,
    start_time TIMESTAMP NOT NULL,
    end_time   TIMESTAMP NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT NOW(),
    CONSTRAINT booking_time_valid CHECK (end_time > start_time)
);
```

Решения и причины:

- `SERIAL PRIMARY KEY` — сервер сам выдаёт идентификатор; `insert_returning_id()`
  сразу получает его через `RETURNING id`.
- `UNIQUE` на телефоне и номере стола — бизнес-правило «один телефон = один гость»,
  «номер стола не повторяется».
- `REFERENCES ... ON DELETE CASCADE` — удаление пользователя или стола убирает его брони,
  иначе в базе остались бы «висячие» записи.
- `CHECK (end_time > start_time)` — защита от нулевого и отрицательного интервала на
  уровне сервера, даже если в коде появится ошибка.
- `IF NOT EXISTS` — повторный запуск не падает.
- Индекс `(table_id, start_time, end_time)` ускоряет поиск пересекающихся броней.

## 3. Слои приложения

```text
app.py            CLI: меню, ввод, вывод
    ↓
backend.py        бизнес-правила: CRUD, проверка доступности, понятные ошибки
    ↓
models/*.py       структуры данных: User, Table, Booking (dataclasses)
    ↓
postgres_driver.py  соединение, DDL, fetch/execute, возврат id
    ↓
PostgreSQL
```

Почему так:

- **модели** не знают про SQL — их можно переиспользовать в любом интерфейсе;
- **драйвер** не знает про бизнес-правила — его можно скопировать в другой проект;
- **backend** — единственное место, где проверяются пересечения и уникальность;
- **CLI** не содержит SQL — только ввод и печать.

Правило то же, что в VPc06: `%s` для значений, `sql.Identifier` для имён объектов,
f-строки — только со статическими именами полей после проверки.

## 4. Логика пересечения бронирований

Главная часть задания. Два интервала пересекаются, если **начало одного раньше конца
другого и конец одного позже начала другого**:

```sql
WHERE table_id = %s
  AND id <> %s
  AND start_time < %s   -- начало существующей < конец новой
  AND end_time   > %s;  -- конец существующей > начало новой
```

Разбор на примерах (бронь 12:00–14:00 уже есть):

| Новый интервал | Пересечение? | Почему |
|---|---|---|
| 13:00–15:00 | да | 12:00 < 15:00 и 14:00 > 13:00 |
| 11:00–13:00 | да | 12:00 < 13:00 и 14:00 > 11:00 |
| 10:00–12:00 | нет | конец 14:00 > начало 10:00, но начало 12:00 < конец 12:00 — ложь |
| 14:00–16:00 | нет | стык: конец предыдущей = начало новой |

Именно поэтому в условии строгие `<` и `>`: равные границы допустимы.

`id <> %s` нужен при обновлении брони: текущая запись не должна мешать сама себе.

## 5. CRUD и безопасность

Создание через `RETURNING id`:

```python
user_id = self.driver.insert_returning_id(
    "INSERT INTO users (name, phone) VALUES (%s, %s) RETURNING id;", (name, phone)
)
```

Обновление с необязательными полями собирается динамически, но **имена полей —
статические**, поэтому f-строка здесь безопасна:

```python
fields, values = [], []
if name is not None:
    fields.append("name = %s")
    values.append(name.strip())
...
values.append(user_id)
self.driver.execute(f"UPDATE users SET {', '.join(fields)} WHERE id = %s;", values)
```

Значения по-прежнему передаются через `%s`. В `count_rows()` имя таблицы проверяется
белым списком — та же схема, что в предыдущем проекте.

Уникальность и внешние ключи не дублируются в коде: база сама отклонит нарушение, а
`backend` переводит `UniqueViolation` в понятное сообщение.

## 6. CLI

`app.py` — цикл меню:

```text
1. Пользователи      → список / добавить / изменить / удалить
2. Столы             → список / добавить / изменить / удалить
3. Бронирования      → список / создать / изменить / удалить
4. Проверить доступность стола
0. Выход
```

Пункт 4 — обязательная по заданию команда: спрашивает стол и интервал, печатает
`СТОЛ СВОБОДЕН` или `СТОЛ ЗАНЯТ`.

Ошибки бизнес-правил (`BookingError`) печатаются строкой «Ошибка: …», программа
продолжает работу. Аварийные ситуации (нет связи с сервером, неверный пароль) — код
выхода 1 и подсказка.

## 7. Грабли

| Граблю | Причина | Решение |
|---|---|---|
| `UnicodeDecodeError` вместо текста ошибки | `lc_messages = 'Russian_Russia.1251'` | `readable_server_error()`: байты из `exc.object`, декодирование в cp1251 |
| После `UniqueViolation` ничего не работает | транзакция помечена как прерванная | `with conn:` откатывает её при исключении, соединение снова пригодно |
| Стык интервалов отвергается | в условии `<=` вместо `<` | строгие `<` и `>` |
| Бронь меняется сама с собой конфликтует | проверка при обновлении | `ignore_booking_id` в `check_table_availability` |
| Время «прыгает» | `TIMESTAMP` без часового пояса | для одного часового пояса допустимо, для многих нужен `TIMESTAMPTZ` |

## 8. Проверка на живой базе

`smoke_test.py` — 20 проверок, все зелёные (`Итого: OK 20, FAIL 0`):

- CRUD пользователей (создание, уникальность телефона, обновление, чтение, удаление);
- CRUD столов;
- создание брони и удаление;
- свободный интервал, занятый интервал, разрешённый стык;
- отказ при пересечении на создании и на обновлении;
- отказ при нулевом интервале.

`seed_demo.py` создаёт 3 пользователя, 3 стола и 2 брони; повторный запуск не дублирует.
